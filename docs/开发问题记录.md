# wz-agent 开发问题与解决记录

> 从零开发 wz-agent（Python 编码 Agent，DeepSeek + ReAct 循环）过程中踩过的坑、根因与解法。
> 每项：**现象 → 原因 → 解决 → 涉及文件**。按类别整理。

---

## 一、Windows 环境特有

### 1. GBK 控制台编码崩溃（emoji / 特殊字符）
- **现象**：运行时报 `UnicodeEncodeError: 'gbk' codec can't encode character '⚠' / '✅'`，agent 中断。
- **原因**：Windows 控制台/重定向默认编码 cp936（GBK）。中文可编码，但 emoji（⚠ ✅）、特殊 Unicode 无法编码。LLM 自由输出常带这类字符。
- **解决**：
  - `interactive.print_human()` 做编码兜底——只替换无法编码的字符（`errors="replace"`），中文保留；
  - main.py 的 rich 输出移除 emoji（✅→"完成"），避免 rich legacy 渲染崩溃。
- **文件**：`src/agent/interactive.py`、`src/main.py`

### 2. UTF-8 批处理文件在 cmd 下崩溃（run.bat 双击闪退）
- **现象**：双击 run.bat 窗口一闪而过，报一堆 `'...echo' 不是内部或外部命令`。
- **原因**：Windows cmd 用 **GBK** 解析 .bat 文件，UTF-8 中文被误读后发生字节错位，把命令结构拆坏（连 `pause` 都被污染成"不存在"）。
- **解决**：run.bat 改**纯 ASCII**（提示用英文）；中文输出交给 Python 程序（GBK 下正常）。
- **文件**：`run.bat`

### 3. bash 子进程 stderr 解码崩溃（`NoneType.strip`）
- **现象**：bash 工具反复报 `错误：工具 'bash' 执行异常 —— 'NoneType' object has no attribute 'strip'`。
- **原因**：`subprocess.run(text=True)` 用 locale（GBK）解码子进程输出。当 stderr 含非 GBK 字节（如 node 输出的 UTF-8 中文）时，读取线程抛 `UnicodeDecodeError`，导致该流属性变成 `None`；随后 `result.stderr.strip()` 对 None 调用 `.strip()` 崩溃。
- **解决**：`subprocess.run` 加 `errors="replace"`（非法字节替换为 �，流不再变 None）；结果处理用 `(result.stdout or "")` 防御。
- **文件**：`src/agent/tools/bash.py`

### 4. bash 超时杀不干净子进程
- **现象**：命令 30s 超时后，python 子进程还在后台跑；agent 反复重试，进程堆积、系统变卡（"一直卡在这里"）。
- **原因**：Windows `subprocess.run(shell=True, timeout=...)` 超时时只杀 cmd.exe，**cmd 启动的子进程是独立的，不会跟着被杀**。
- **解决**：改用 `Popen` + 超时后 `taskkill /pid <pid> /T /F` **强制终止整棵进程树**（POSIX 用 `proc.kill()`）。
- **文件**：`src/agent/tools/bash.py`

### 5. Windows 管道输入引入 surrogate
- **现象**：`'utf-8' codec can't encode character '\udcae': surrogates not allowed`，OpenAI json 序列化失败。
- **原因**：Windows 管道喂入中文时，输入流编码转换产生**孤立 surrogate**（U+D800-DFFF）。
- **解决**：`interactive.strip_surrogates()` 清理；在读入（`prompt_human`）和调 LLM 前（`_run_loop`）都清理。
- **文件**：`src/agent/interactive.py`、`src/agent/loop.py`

### 6. rich markup 吞掉 `[auto]`
- **现象**：终端显示 `Agent 思考中... (bash: )`，`[auto]` 不见了。
- **原因**：rich 把 `[...]` 当样式标记解析，`[auto]` 不是合法样式名被吞。
- **解决**：`[auto]` → `[[auto]]` 转义。
- **文件**：`src/main.py`

## 二、Agent 健壮性

### 7. 工具参数 JSON 解析崩溃
- **现象**：`json.loads(call["function"]["arguments"])` 抛 `JSONDecodeError: Unterminated string`，**整个程序崩溃**。
- **原因**：LLM 写大文件（如 200 球员数据的 script.js）时，工具参数超长被 API 截断 → 不是合法 JSON。
- **解决**：`json.loads` 包 try/except——参数非法时不执行工具、不崩溃，把错误作为工具结果返回给 LLM，让它重新生成完整参数。
- **文件**：`src/agent/loop.py`

### 8. 消息上下文无限膨胀
- **现象**：ReAct 循环中 messages 无限增长，长任务超 context 上限。
- **解决**：`_maybe_compact()` 历史压缩——超过预算时保留 system + 首条 user + 最近 N 轮，丢弃早期轮次。按"轮"（assistant 或 user 封轮）裁剪，保证 assistant/tool 成对、不产生孤立 tool 消息。
- **文件**：`src/agent/loop.py`

### 9. 单轮工具调用步数不够
- **现象**：澄清阶段多轮问答（每个 ask_user 消耗一步）+ 写 spec，10 步内写不完，报 `[WARN] 已达到最大步数限制`。
- **解决**：会话内 `SESSION_MAX_STEPS` 提到 30，一次性模式同步。
- **文件**：`src/agent/session.py`

### 10. LLM 调用无显式超时（待完善）
- **现状**：`_get_client()` 创建 client 时未设 `timeout`，依赖 OpenAI SDK 默认（约 600s）；流式模式无空闲超时。
- **已有**：bash 工具 30s 超时（问题 4）。
- **待办**：LLM 调用显式 timeout + 流式空闲超时（讨论过，尚未实现）。

## 三、交互与意图识别

### 11. clarify 问完一轮就退出（无对话循环）
- **现象**：澄清阶段 agent 问完问题程序就退出；用户回答要重新运行命令，且 agent 跨轮"失忆"。
- **原因**：一次运行 = 一次 ReAct 循环，`_run_loop` 纯文本回复即返回，不写回历史、无循环。
- **解决**：`run_interactive()` 对话循环（agent 返回问题 → 等用户回答 → 追加历史 → 继续）；`_run_loop` 纯文本分支先把回复写回 messages。
- **文件**：`src/agent/loop.py`

### 12. 用户提问被当需求
- **现象**：用户问"你的数据来源在哪"，agent 当新需求开始追问"什么项目"。
- **原因**：会话把非命令输入一律当需求；clarify 没判断输入类型。
- **解决**：
  - clarify prompt 加"判断输入类型"（非需求 → 直接回答）；
  - 会话层 `_is_question()` 检测提问 → `run_qa()` 直接回答。
- **文件**：`src/agent/prompts/clarify.py`、`src/agent/session.py`

### 13. 意图识别死板（说"编码"被当需求）
- **现象**：用户说"开始编码吧"不触发编码，被当需求澄清。
- **原因**：`is_code_intent` 只精确匹配"编码"等词。
- **解决**：`is_code_intent` 识别短指令（≤8 字含触发词，如"开始编码吧""去实现"），长需求描述不误判。
- **文件**：`src/agent/session.py`

### 14. 需求确认环节把"去编码"当补充
- **现象**：确认环节用户说"编码吧"，被当作补充需求整合进 spec。
- **解决**：`_confirm_requirements` 识别编码意图（直接进入编码）和"无补充"表达（退出确认），而不是当补充整合。
- **文件**：`src/agent/session.py`

### 15. 回答太激进（非提问也被"回答"）
- **现象**：`_is_question` 见"吗/呢/什么"就触发 `run_qa`，用户觉得"我不是每次输入都是回答"。
- **解决**：收紧 `_is_question`——只有问号结尾、短问句"吗"结尾、或强疑问词（是啥/为什么/怎么等）才回答。
- **文件**：`src/agent/session.py`

### 16. 语气词/无内容输入也触发
- **现象**：用户说"嗯""好的""继续"，agent 也去改代码/澄清。
- **解决**：`_is_noop_input()` 忽略语气词/过短输入；`_is_requirement()` 只有明确需求表达（帮我/做一个/开发等）才进澄清；无法识别的输入直接提示。
- **文件**：`src/agent/session.py`

### 17. 澄清询问太多/打包问题
- **现象**：澄清阶段为覆盖领域清单连问多个问题，或一个问题打包多个子问题。
- **解决**：clarify prompt 明确**一轮只问一个聚焦问题、不打包**；可多问但问清为止；需求明确时不问。
- **文件**：`src/agent/prompts/clarify.py`

## 四、工程实践

### 18. 项目零测试
- **现象**：1800+ 行代码无任何自动化测试。
- **解决**：补 pytest 单元测试，覆盖 issues / edit / bash / base / loop / interactive / session / runtime / read / write 等。现 **128 例全绿**。
- **文件**：`tests/`

### 19. `.env` 加载顺序 bug
- **现象**：用 `.env` 配置 key 不生效（client 永远用占位符 `sk-xxx`）。
- **原因**：`load_dotenv()` 在 `import agent` **之后**调用，而 `loop.py` 在 import 时就创建 `OpenAI(api_key=...)` 固化了占位符。
- **解决**：client 改**惰性初始化**（`_get_client()` 首次调用时读环境变量）。
- **文件**：`src/agent/loop.py`

### 20. 大文件写截断 / 读不全
- **现象**：写大文件单次参数过长被截断（见问题 7）；读大文件只能看开头 2000 字符，无法看中后部分。
- **解决**：
  - `write` 加 `append` 参数（分块追加写大文件）；
  - `read` 加 `lines` 参数（`"1-50"` / `"40"` 按行范围读，带行号）；
  - code prompt 指导 agent 大文件分块写、分段读。
- **文件**：`src/agent/tools/write.py`、`src/agent/tools/read.py`、`src/agent/prompts/code.py`

### 21. 运行产物散落
- **现象**：spec.md、生成的代码散落在项目根，难找、易混乱。
- **解决**：`runtime.start_run()` 为每次运行建独立工作区 `runs/<时间戳>/`，集中放 `spec.md`、`output/`（代码）、`session.log`（agent 流式输出回放）；`runs/` 进 gitignore。
- **文件**：`src/agent/runtime.py`

### 22. 需求澄清文档与实现不符
- **现象**：README 写 clarify"逐轮深入追问"，实际代码是"问完一轮就退出"。
- **解决**：实现 `run_interactive` 对话循环（见问题 11），文档与实现对齐。

---

## 经验总结

1. **Windows 是最大的坑**：GBK 编码、cmd 批处理、进程树、管道 surrogate——所有编码相关崩溃都源于"Windows 用 GBK 而程序按 UTF-8 假设"。
2. **Agent 的输出不可信**：LLM 可能返回截断参数、超长内容、非预期格式——所有解析点（json.loads 等）都要防御。
3. **用户意图要收敛**：从"什么都当需求"到"明确需求才澄清、明确提问才回答、语气词忽略"，规则宁可收敛不可激进。
4. **运行可回放**：session.log 保存流式输出，让"看 agent 当时做了什么"成为可能——调试成本大幅下降。
