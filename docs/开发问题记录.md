# wz-agent 开发问题与解决记录

> 从零开发 wz-agent（Python 编码 Agent，DeepSeek + ReAct 循环）过程中踩过的坑、排查过程与解法。
> 每项按 **问题现象 → 分析过程 → 修改方法** 展开，方便复现和借鉴排查思路。

---

## 一、Windows 环境问题

### 1. GBK 控制台编码崩溃（emoji / 特殊字符）

**问题现象**
- 流式打印时直接崩：`UnicodeEncodeError: 'gbk' codec can't encode character '⚠'（U+26A0）in position 2`。
- 用 rich 输出 `✅` 也崩：`UnicodeEncodeError: 'gbk' codec can't encode character '✅'（U+2705）`（rich 的 legacy Windows renderer）。
- agent 一输出含 emoji 的内容就中断，看起来"莫名其妙崩掉"。

**分析过程**
- 第一次用 FakeClient 模拟流式时，发现打印 `↳`（U+21B3）崩——当时以为只是个符号问题，改成 `->`。
- 后来真实 API 冒烟（管道喂需求）时，LLM 输出的内容里带了 `⚠`/`✅`，`print` 直接抛 `UnicodeEncodeError`。定位到：Windows 控制台/重定向默认编码是 **cp936（GBK）**，中文可以编码，但 emoji 和部分 Unicode（U+2000 以上非 CJK）无法编码。
- 关键认识：**LLM 自由输出不可控**，任何字符都可能出现，打印必须做编码兜底，而不是假设"中文就够"。
- 用最小复现确认：`print("⚠")` 在 GBK 终端必崩，验证了根因。

**修改方法**
- `interactive.print_human()`：先正常 `print`；捕获 `UnicodeEncodeError` 后，用 `text.encode(当前输出编码, errors="replace").decode()` 重打——**只替换无法编码的字符**（如 `⚠`→`?`），中文保留（不能整个字符串 ascii 化，否则中文全变 `?`）。
- 流式文本、工具调用展示、交互提示全部改走 `print_human`。
- main.py 的 rich 字符串移除 emoji（`✅ 完成` → `完成`），避免 rich legacy 渲染崩溃。
- 涉及文件：`src/agent/interactive.py`、`src/main.py`。

### 2. UTF-8 批处理文件在 cmd 下崩溃（run.bat 双击闪退）

**问题现象**
- 用户双击 run.bat，"弹框就没了"（窗口一闪而过）。
- 在 cmd 里执行 bat 报一堆 `'...echo' 不是内部或外部命令`、`'...pause' 不是内部或外部命令`。

**分析过程**
- 先怀疑 cmd 里 `python` 找不到——验证 `cmd /c "python --version"` 正常，排除。
- 完整路径执行 bat，看到输出里中文变成乱码且**命令被拆散**：`'��动生成代�?echo'` 不是命令。典型的中文编码错位。
- 根因：Windows cmd 用 **GBK** 解析 .bat 文件。bat 是 UTF-8 编码（Write 工具写的），UTF-8 的中文字节在 GBK 下被误读，字节序列里碰巧出现命令分隔符，导致**整行被拆坏**——连 `pause >nul`（让窗口停留的命令）都被污染成"不存在"，所以窗口一闪就关。
- 试过 `chcp 65001` 无效：cmd 对 bat **文件的解析**用的是启动代码页，不是显示代码页，`chcp` 救不了 UTF-8 中文 bat。

**修改方法**
- run.bat 改成**纯 ASCII**（框架提示用英文），中文输出全部交给 Python 程序（Python 在 GBK 控制台输出中文是正常的）。
- 涉及文件：`run.bat`。

### 3. bash 子进程 stderr 解码崩溃（`NoneType.strip`）

**问题现象**
- 会话里 bash 工具反复报：`错误：工具 'bash' 执行异常 —— 'NoneType' object has no attribute 'strip'`。
- 成功的命令（`node --check game.js`）和失败的命令（`node _test.js`）行为不一致——执行脚本的总是崩。

**分析过程**
- 先全局搜 `.strip()`，怀疑对象：bash 工具的 `command.strip()` 或 `result.stdout/stderr.strip()`。
- 用**最小复现**直接跑失败的命令：`subprocess.run("node _test.js", shell=True, capture_output=True, text=True)`，结果——
  - `stdout: 'PLAYERS 数量: 80\n'`（正常）
  - `stderr: None`（异常！）
  - 同时日志里出现 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xae`（在 `_readerthread` 线程）。
- 根因链：`subprocess.run(text=True)` 在 Windows 用 locale 编码（GBK）解码子进程 stdout/stderr → node 的 stderr 含非 GBK 字节（UTF-8 中文）→ 读取线程抛 `UnicodeDecodeError` → **该流属性变成 `None`** → bash 里 `result.stderr.strip()` 对 None 调用 `.strip()` → 崩溃。

**修改方法**
- `subprocess.run` 加 `errors="replace"`：解码时非法字节替换为 `�`，读取线程不再抛异常、流不再变 None。
- 结果处理加 None 防御：`(result.stdout or "")` / `(result.stderr or "")`。
- 加回归测试（模拟 stdout/stderr 为 None、stderr 有内容）。
- 涉及文件：`src/agent/tools/bash.py`。

### 4. bash 超时杀不干净子进程

**问题现象**
- 会话里 agent 跑 `python _fetch_espn.py`（抓 ESPN 30 队名单），"一直卡在这里"。
- 即使 bash 有 30s 超时，脚本还在后台跑，agent 反复重试，系统越来越卡。

**分析过程**
- 先读 `_fetch_espn.py`：遍历 35 个球队 ID，每个发一个 ESPN HTTP 请求（`urlopen(timeout=15)`），最坏 35×15≈8.7 分钟。
- 实测 ESPN 接口：单个请求 2.6s → 35 个约 100s，远超 bash 30s 超时。
- 关键：`subprocess.run(shell=True, timeout=30)` 超时时抛 `TimeoutExpired`，但 Windows 上启动的是 `cmd.exe /c python ...`，**超时只杀 cmd.exe，cmd 的子进程（python）是独立的，不会跟着被杀** → python 残留后台，agent 以为超时又重试，进程堆积。

**修改方法**
- 从 `subprocess.run` 改 `subprocess.Popen` + `communicate(timeout=...)`。
- 超时时调用 `_kill_process_tree()`：Windows 用 `taskkill /pid <pid> /T /F` **强制终止整棵进程树**（cmd → python 全杀）；POSIX 用 `proc.kill()`。
- 真实验证：`sleep 120` 的命令 30.2s 正确返回 `[ERR] 超时（>30s）：已连同子进程强制终止`，不再挂起。
- 涉及文件：`src/agent/tools/bash.py`。

### 5. Windows 管道输入引入 surrogate

**问题现象**
- 管道喂需求时（`printf '中文' | python src/main.py`）报：`'utf-8' codec can't encode character '\udcae': surrogates not allowed`，OpenAI json 序列化失败，agent 返回 `[API-ERR]`。

**分析过程**
- `\udcae` 是**孤立 surrogate**（U+DC80-DCFF 区间），通常来自 Python 解码非 UTF-8 字节时用的 `surrogateescape` 机制。
- Windows 管道喂 UTF-8 中文，Python 的 stdin 按某种编码（GBK/utf-8）解码，遇到非法字节保留为 surrogate → 这些字符被塞进 messages → 发给 OpenAI 时 json 序列化失败。
- 真实 TTY 不会触发（控制台用 UTF-16 I/O），但脚本化/管道场景必现。

**修改方法**
- `interactive.strip_surrogates(text)`：去掉 U+D800-DFFF 区间字符。
- `prompt_human` 读入后清理；`_run_loop` 每次调 LLM 前对 messages 的 content 统一清理（防御所有来源）。
- 涉及文件：`src/agent/interactive.py`、`src/agent/loop.py`。

### 6. rich markup 吞掉 `[auto]`

**问题现象**
- 终端显示 `Agent 思考中... (需求澄清, bash: )`，`[auto]` 不见了（`bash: [auto]` 只剩 `bash: `）。

**分析过程**
- 排查输出格式，发现 `console.print(f"...bash: {mode_label}[/]")` 里 `mode_label` 是 `"[auto]"`——rich 把 `[...]` 当**样式标记**解析，`[auto]` 不是合法样式名，被吞掉。
- 同理 `[plan]` 也会被吞。

**修改方法**
- rich markup 里方括号翻倍转义：`[auto]` → `[[auto]]`（rich 显示为 `[auto]`）。
- 涉及文件：`src/main.py`。

## 二、Agent 健壮性

### 7. 工具参数 JSON 解析崩溃

**问题现象**
- 会话里 agent 写 script.js（约 200 球员数据）时，整个程序崩溃，traceback 末尾：
  ```
  File "loop.py", line 419, in _run_loop
      tool_args = json.loads(call["function"]["arguments"])
  json.decoder.JSONDecodeError: Unterminated string starting at: line 1 column 13
  ```
- 窗口直接"Done. Press any key to close."，agent 死了。

**分析过程**
- traceback 明确指向 `json.loads`——LLM 返回的工具调用 `arguments` 不是合法 JSON。
- 触发场景是**写大文件**：LLM 一次生成含 200 球员数据的超长 write 参数，被 API 截断 → JSON 字符串未闭合（`Unterminated string`）。
- 这是核心健壮性缺陷：任何解析 LLM 输出的点都不可信，必须防御。

**修改方法**
- `json.loads` 包 try/except（捕获 `json.JSONDecodeError` 和 `ValueError`）。
- 参数非法时：**不执行工具、不崩溃**，把错误作为 tool 结果返回给 LLM（`[ERR] 工具 'write' 的参数不是合法 JSON：... 请重新生成完整、闭合的参数`）→ LLM 看到后重新生成（会缩小内容或分段写）。
- 加测试：模拟 LLM 返回非法 JSON 参数，验证不崩溃、错误返回给 LLM、继续跑完。
- 涉及文件：`src/agent/loop.py`。

### 8. 消息上下文无限膨胀

**问题现象**
- 长任务（多轮澄清 + 多模块编码）中，messages 无限增长，最终可能超 DeepSeek context 上限。

**分析过程**
- ReAct 循环里每条 LLM 消息、工具结果都 append 进 messages，`max_steps` 只限制步数、不限制 token 总量。
- 估算：单轮 LLM 回复 + 工具结果约 1-4k 字符，几十轮后几万字符，长任务必然触顶。

**修改方法**
- `_maybe_compact()` 历史压缩：消息总量超预算（40k 字符）时，保留 system + 首条 user（任务定义）+ **最近 KEEP_HISTORY_ROUNDS 轮**，丢弃早期中间轮次，并插入一条 system 提示"较早记录已移除"。
- 按"轮"为单位裁剪，**assistant 或 user 都封轮**（交互模式下用户回答/注入指令是独立轮，不能误裁）；保证 assistant 与其 tool 结果成对，不产生 OpenAI 拒绝的孤立 tool 消息。
- 涉及文件：`src/agent/loop.py`。

---

### 9. 单轮工具调用步数不够

**问题现象**
- 会话里澄清写完 spec 后报：`[WARN] 已达到最大步数限制（10 步），Agent 未完成任务`，spec.md 未生成。

**分析过程**
- 澄清采用"多问问清楚"：每个 `ask_user` 消耗一步，问 5-8 个问题 + 最后写 spec，10 步就触顶。
- 步数上限（max_steps=10）是为单任务设计的，不匹配"多轮问答"的澄清。

**修改方法**
- 会话内 `SESSION_MAX_STEPS` 提到 30（澄清多轮问答 + 编码分模块都够），一次性模式同步。
- 涉及文件：`src/agent/session.py`、`src/main.py`。

---

### 10. LLM 调用无显式超时（待完善）

**问题现象**
- agent 思考时如果 DeepSeek 卡住，屏幕完全无动静，最多等 SDK 默认（约 600s / 10 分钟）才报错，像"死机"。

**分析过程**
- `_get_client()` 创建 `OpenAI(...)` 时未设 `timeout`，走 SDK 默认 600s。
- 流式模式（`stream=True`）也没有"多久没有新 chunk 就中断"的空闲超时。

**现状 / 待办**
- 已有防护：bash 30s 超时（问题 4）、步数/轮次上限。
- 待办：LLM 调用显式 `timeout` + 流式空闲超时（已讨论过，尚未实现）。
- 涉及文件：`src/agent/loop.py`。

## 三、交互与意图识别

### 11. clarify 问完一轮就退出（无对话循环）

**问题现象**
- 澄清阶段 agent 问出问题后**程序就退出了**；用户回答要重新运行命令，且新运行 agent 不记得上一轮答了什么（"失忆"）。

**分析过程**
- 一次运行 = 一次 ReAct 循环。`_run_loop` 遇到纯文本回复就 `return`，**不把回复写回 messages** → 下一轮没有历史。
- 澄清的"逐轮追问"实际没实现（README 说"逐轮深入追问"，代码是一次性）。

**修改方法**
- `run_interactive()` 对话循环：agent 返回普通文本（问题）→ `prompt_human` 等用户回答 → 追加为 user 消息 → 继续，直到回复以 `[DONE]` 等终止前缀开头。
- `_run_loop` 纯文本分支先把回复写回 messages（`messages.append({"role":"assistant","content":content})`）。
- 涉及文件：`src/agent/loop.py`。

### 12. 用户提问被当需求

**问题现象**
- 会话里用户问"你的数据来源在哪"，agent 当新需求开始追问"你说的数据来源是指什么项目？"。

**分析过程**
- 会话把非命令输入一律当需求 → `run_clarify`。
- clarify 的 agent 没有判断"这是提问还是需求"，直接把提问当需求澄清。

**修改方法**
- clarify prompt 加"判断输入类型"：非需求（对 agent 的提问/闲聊）→ 直接回答，回复以 `[DONE]` 结束，不写 spec、不用 ask_user 追问。
- 会话层加 `_is_question()` 检测提问 → `run_qa()` 直接回答（结合当前 spec/代码上下文）。
- 涉及文件：`src/agent/prompts/clarify.py`、`src/agent/session.py`。

---

### 13. 意图识别死板（说"编码"被当需求）

**问题现象**
- 用户说"开始编码吧""去实现"，agent 没去编码，而是当需求澄清。
- 反过来，"帮我实现一个游戏"（需求）若只按词匹配又会被误判成编码。

**分析过程**
- `is_code_intent` 最初只做**精确匹配**（`line in CODE_TRIGGERS`），"开始编码吧"带"吧"就不匹配 → 落到需求分支。

**修改方法**
- `is_code_intent` 改为两种形态都算：精确匹配触发词（`编码`/`实现`/`code`），或**短指令**（≤8 字且含触发词，如`开始编码吧`/`去实现`/`现在开始`）。
- 长需求描述（`帮我实现一个游戏`，>8 字）不会误判。
- 涉及文件：`src/agent/session.py`。

### 14. 需求确认环节把"去编码"当补充

**问题现象**
- 澄清写完 spec 后进入"还需要补充什么吗？"确认环节，用户说"编码吧"，agent 却把它当成补充需求整合进 spec。

**分析过程**
- `_confirm_requirements` 的循环里，任何非空输入都默认当作"补充内容"整合——没识别"用户想开始编码/需求已完整"的意图。

**修改方法**
- 确认环节依次判断：提问 → `run_qa` 回答后继续；编码意图（`编码吧`/`去实现`）→ **直接进入编码**；"无补充"表达（`没有补充了`/`就这样`/`不用了`）→ 退出确认；语气词（`嗯`/`好的`）→ 视为无补充退出；其他 → 当补充整合。
- 涉及文件：`src/agent/session.py`。

---

### 15. 回答太激进（非提问也被"回答"）

**问题现象**
- 用户说"这个游戏能玩吗"被回答合理，但很多非提问输入（含"吗/呢/什么"的普通陈述）也被 `run_qa` "回答"，用户反馈"我不是每次输入都是回答"。

**分析过程**
- `_is_question` 最初用 `("吗","呢","什么",...)` 做子串匹配，太宽——很多非提问句子也含这些词。

**修改方法**
- 收紧 `_is_question`：只有**问号结尾**、**短问句以"吗"结尾**（≤12 字）、或**强疑问词**（`是啥`/`是什么`/`为什么`/`怎么`/`如何`等）才算提问。
- 涉及文件：`src/agent/session.py`。

---

### 16. 语气词/无内容输入也触发

**问题现象**
- 用户说"嗯""好的""继续"，agent 也去改代码/澄清/回答。

**分析过程**
- 会话分发没有"无意图输入"过滤，语气词落到兜底分支（改代码/澄清）。

**修改方法**
- `_is_noop_input()`：语气词/确认词（`嗯`/`好的`/`ok`/`继续`等）或过短输入（≤1 字）→ **直接忽略**。
- `_is_requirement()`：只有明确需求表达（`帮我`/`做一个`/`开发`/`写一个`等动作词）才进需求澄清。
- 无法识别的输入 → 提示"没理解你的意思"，**不触发任何 agent 动作**。
- 涉及文件：`src/agent/session.py`。

---

### 17. 澄清询问太多/打包问题

**问题现象**
- 澄清阶段 agent 为覆盖领域清单（功能/技术栈/数据/交互/边界/交付 6 项）连问多个问题，甚至一个问题里打包多个子问题（"用什么语言？要数据库吗？界面什么样？"）。

**分析过程**
- clarify prompt 的领域清单让 agent 觉得"要覆盖全部"，每个缺口都 `ask_user`；且没约束"一次一个问题"。
- 用户反馈"没有一轮一轮询问，会在一次会话中询问多个问题"。

**修改方法**
- clarify prompt 明确：**一轮只问一个聚焦问题、绝不打包**；可多问但问清为止；需求描述足够明确时**不追问直接写 spec**。
- 涉及文件：`src/agent/prompts/clarify.py`。

- 关键：文件系统操作全部重定向到 `tmp_path`，`input()`/`print` 用 monkeypatch，避免测试污染真实环境。
- 涉及文件：`tests/`。

### 19. `.env` 加载顺序 bug

**问题现象**
- 用 `.env` 文件配置 API key 不生效，agent 一直用占位符 `sk-xxx`（认证失败）。
- 用系统环境变量（README 推荐方式）却正常。

**分析过程**
- 排查 `load_dotenv()` 的调用时机：main.py 里 `from agent.loop import run`（import 时创建 `OpenAI(api_key=os.environ.get(...))`）**先于** `load_dotenv()`。
- 实验确认：`OpenAI(api_key=...)` 构造后 key 被固化，之后的 `load_dotenv()` 不会更新 client → `.env` 的 key 永远不生效。
- 用系统环境变量正常，因为 import 时 `os.environ` 已有值。

**修改方法**
- client 改**惰性初始化**：`_get_client()` 首次调用时才读环境变量创建（复用全局单例），保证无论 `load_dotenv()` 何时调用都能拿到正确 key。
- 涉及文件：`src/agent/loop.py`。

### 20. 大文件写截断 / 读不全

**问题现象**
- 写大文件（如 200 球员数据的 JS）单次参数过长被截断（见问题 7，导致崩溃）。
- 读大文件只能看开头 2000 字符，无法看中后部分——agent 改 5000 行文件时找不到要改的位置。

**分析过程**
- write 一次接收完整 content，无分块机制；read 只有前 3000 字符截断（loop 再 2000 截断），无指定区域读取。

**修改方法**
- `write` 加 `append` 参数：`write(path, content, append=True)` 追加到末尾，支持分块写大文件。
- `read` 加 `lines` 参数：`read(path, lines="1-50")` / `"40"` 按行范围读取，**带行号**返回（便于 edit 定位）。
- code prompt 指导 agent：大文件先用 write 写骨架再 append 分段；读大文件用 read lines 分段读。
- 涉及文件：`src/agent/tools/write.py`、`src/agent/tools/read.py`、`src/agent/prompts/code.py`。

### 21. 运行产物散落

**问题现象**
- spec.md、生成的代码（game.js、index.html 等）、临时调试文件散落在项目根，难找、易混乱，还容易被误提交。

**分析过程**
- 编码产物默认写到项目根（write 相对 cwd），spec 也在项目根；agent 抓数据时还产生一堆 `_xxx.py`/`.json` 临时文件。

**修改方法**
- `runtime.start_run()` 为每次运行建独立工作区 `runs/<时间戳>/`：集中放 `spec.md`、`output/`（生成的代码）、`session.log`（agent 流式输出回放）。
- `runs/` 加进 `.gitignore`。
- 涉及文件：`src/agent/runtime.py`。

### 22. 需求澄清文档与实现不符

**问题现象**
- README 写 clarify"逐轮深入追问直到需求明确"，实际代码是"问完一轮就退出，回答要重新运行"。

**分析过程**
- 文档描述的是理想行为，代码是批处理（一次运行一轮）；文档没跟上实现演进。

**修改方法**
- 实现 `run_interactive` 对话循环（见问题 11），让文档与实现对齐。
- 涉及文件：`src/agent/loop.py`。

## 经验总结

1. **Windows 是最大的坑**：GBK 编码、cmd 批处理、进程树、管道 surrogate——几乎所有编码相关崩溃都源于"Windows 用 GBK 而程序按 UTF-8 假设"。所有面向终端的输出都要做编码兜底。
2. **Agent 的输出不可信**：LLM 可能返回截断参数、超长内容、非预期格式——所有解析点（`json.loads`、参数校验）都要防御，把错误回喂而不是崩溃。
3. **用户意图要收敛**：从"什么都当需求"演进到"明确需求才澄清、明确提问才回答、语气词忽略、非意图不触发"。规则宁可收敛不可激进。
4. **运行可回放**：`session.log` 保存流式输出，让"看 agent 当时做了什么"成为可能——多个"诡异"问题（bash NoneType、卡住、截断）都是靠它定位的，调试成本大幅下降。
5. **先复现再修**：每个 bug 都用最小复现（真实跑失败的命令、traceback、session.log）确认根因，再动手改，避免"猜着修"。
