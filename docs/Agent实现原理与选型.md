## 第 1 章 Agent 的组成：核心公式

### 1.1 Agent = LLM + 上下文 + 工具

现代 Agent 的最小工程公式：

> **Agent = LLM（大脑）+ 上下文（眼睛）+ 工具（手脚）**，三者缺一不可。

- **LLM 是大脑**——决策核心：解析意图、拆解任务、决定下一步调什么工具
- **上下文是眼睛**——决定它**能看到什么**：系统提示词、工具定义、消息历史
- **工具是手脚**——决定它**能做什么**：文件读写、命令执行、API 调用

关键认知（观察空间与动作空间理论）：**在模型固定时，提升 Agent 能力最主要的工程手段，就是扩展观察空间（上下文）和动作空间（工具）**。许多看似"需要更聪明模型"的问题，其实只是接口问题——把数据纳入上下文、把操作封装成工具，原本不可解的任务就变得可解。Manus（合并搜索/编码/电脑操控三类空间）和 OpenClaw（把接口延伸到消息渠道和本地文件）的演进都印证了这一点。

### 1.2 Agent 的边界：LLM 与 Harness

展开成边界图：

```
┌─────────────────── Agent ────────────────────┐
│                                              │
│   ┌────────┐                                 │
│   │  LLM    │  ← 唯一不属于 harness 的部分     │
│   │ （大脑） │    （模型权重，你改不了）          │
│   └───┬────┘                                 │
│       │                                      │
│  ─────┼──── 以下全部是 Harness ────────────   │
│       │                                      │
│  ┌────▼─────────────────────────────────┐    │
│  │ ① 上下文管理（眼睛）—— 决定它看到什么    │    │
│  │   系统提示词·轨迹·压缩·记忆            │    │
│  ├──────────────────────────────────────┤    │
│  │ ② 工具接口（手脚）—— 决定它能做什么      │    │
│  │   工具执行·校验·分发                   │    │
│  ├──────────────────────────────────────┤    │
│  │ ③ ReAct 循环（引擎）—— 让三者协同       │    │
│  │   while: 想→做→看→再想                 │    │
│  ├──────────────────────────────────────┤    │
│  │ ④ 约束·验证·纠正（刹车与方向盘）          │    │
│  │   权限·黑名单·失败回喂·熔断             │    │
│  └──────────────────────────────────────┘    │
│                                              │
└──────────────────┬───────────────────────────┘
                   │ 观察通道 / 动作接口
            ┌──────▼──────┐
            │ Environment │ ← 文件系统、终端、网络
            │ （环境，不在 Agent 内）│
            └─────────────┘
```

**Harness 与 Agent 的关系**：Agent = LLM + Harness（边界内），再加 Environment（边界外，与 Agent 闭环交互）。**Harness = Agent 边界内、模型之外的一切**：上下文管理、工具接口、ReAct 循环、约束验证纠正都是它的组成部分——“约束/验证/纠正”是生产级 harness 的保障层，不是 harness 的全部。Environment 虽在模型之外，但不属于 Harness。

一个检验标准：**换个模型，它还成立吗？** ReAct 循环成立、工具执行成立、压缩与记忆成立——与模型无关的都是 harness；只有模型本身的能力（理解、推理）不是。

| 部件 | 职责 | 所属 | wz-agent 对应 | 详见 |
|---|---|---|---|---|
| LLM | 理解、规划、决策 | 大脑（非 harness） | DeepSeek API | 第 2 章 |
| 上下文管理 | 决定模型看到什么 | harness① | system prompt + messages | 第 3 章 |
| 工具接口 | 决定模型能做什么 | harness② | read/write/edit/bash | 第 4 章 |
| ReAct 循环 | 串联三者的引擎 | harness③ | `_run_loop` | 第 5 章 |
| 约束·验证·纠正 | 让它可靠地做事 | harness④ | 权限/自愈/任务系统 | 第 6 章 |

### 1.3 一个反直觉的事实：智能不在你的代码里

Agent 的"智能"——感知、推理、决策——完全来自模型训练，不是工程师编出来的。你写的代码（harness）是给大脑配的载具。**用 if-else、节点图硬编码流程的"Agent 平台"不是 Agent**——模型在里面只是个高级文本填充节点。真正的 Agent 是模型自主决定下一步，你的代码负责执行和传递信息。

这个判断也解释了为什么本文敢用 wz-agent（一个学习项目）演示全部概念：**它的每个部件都足够小、足够真实**——概念不会被框架抽象稀释。

## 第 2 章 LLM：大脑

### 2.1 是什么

大语言模型是 Agent 的决策核心。收到请求后它要：解析真实意图（用户说的往往不是他真正想要的）→ 拆解成可执行步骤 → 持续判断"下一步做什么、调哪个工具、传什么参数"。

这种"理解-规划-执行"能力来自**预训练**——模型不是盲目随机探索，而是在结构化知识体系上推理。2026 年的前沿范式是"**模型即 Agent**"：通过后训练（强化学习）把工具调用内化为原生能力。但模型越强，harness 越关键——**模型自主决策的空间越大，出错的影响面越大**，越需要约束、验证与纠正（第 6 章）。

### 2.2 怎么选

| 选项 | 定位 | 采纳原因 | 适用场景 |
|---|---|---|---|
| OpenAI GPT | 闭源标杆 | 工具调用训练最充分 | 预算充足、要最强效果 |
| Anthropic Claude | 闭源 | 长上下文与编码突出 | 代码生成、长文档 |
| **DeepSeek** | 开源+便宜 | 成本约 GPT 1/10，OpenAI 兼容 API | 预算敏感、可自部署 |
| 本地开源（Qwen 等） | 完全私有化 | 数据不出内网 | 数据合规要求高 |

两个分岔：①闭源 API vs 开源自部署（省事 vs 可控）；②**API 格式**——OpenAI 兼容格式已成事实标准（DeepSeek/Qwen/GLM 都兼容），换模型只改一个 `base_url`。

## 第 3 章 上下文：眼睛

### 3.1 是什么

上下文是 Agent 在每个决策点能看到的**全部信息**——它的"视野"。从 API 视角，每次调用 LLM 时的上下文由五部分构成：

```
上下文 = 静态前缀 + 轨迹（trajectory）

静态前缀（对话中不变）：
  1. 系统提示词    —— Agent 的"岗位说明书"：身份、权限、行为准则
  2. 工具定义      —— 可用工具的名称、功能描述、参数格式

轨迹（随交互增长）：
  3. 用户消息
  4. 模型回复（含思考与工具调用）
  5. 工具执行结果
```

**消融实验表明：去掉任何一部分，系统都显著退化**（没有工具定义，Agent 根本无法识别和调用工具）。

### 3.2 关键工程问题：窗口有限

上下文窗口是固定大小的"草稿纸"。任务一长：超限被 API 拒绝、费用暴涨、注意力涣散。业界的应对（按优先级）：

1. **能不进的就不进**——文件系统当索引，用啥读啥（按需加载）
2. **蒸馏**——把长对话结论沉淀成文件，以后只带文件不带历史
3. **压缩**——超限前裁剪/摘要旧轨迹（必然丢细节，最后手段）

### 3.3 wz-agent 的实现

**静态前缀**（`prompts/` 五份模板）——系统提示词随阶段切换：

```
clarify.py    "你是需求分析师，逐轮追问用户直到需求明确，产出 spec.md"
code.py       "你是编码 agent，按 spec.md 用工具实现，遇错自修"
modify.py / triage.py / to_tickets.py ...
```

注意一个设计决策（`docs/adr/0001`）：**阶段切换由代码控制，不靠模型自觉**——单一 prompt 管多阶段，模型必然在错误时机做错误事（编码中段突然开始追问用户）。

**轨迹管理——蒸馏层**（`context.py`）：阶段一的几十轮澄清对话 → 蒸馏成 spec.md（2KB 需求文件）；阶段二只注入 spec.md 不带原始对话。历史里全是噪音（改口、闲聊、被否决的方案），spec 是蒸馏后的需求。

**轨迹管理——压缩层**（`loop.py:77` `_maybe_compact`，保头裁中留尾）：

```python
head = messages[:2]                    # 静态前缀 + 首条 user（任务定义）
rounds = 最近 KEEP_HISTORY_ROUNDS 轮    # 当前工作状态
messages[:] = head + rounds
# 再插一条 system："较早的工具记录已移除，请基于最新状态继续"
```

三个精妙细节（各来自真实 bug，坑#8）：**"轮"以 assistant 和 user 封轮**（用户回答是独立轮次，不成对保留会误裁）；**assistant 与其 tool 结果永远绑定**（拆开产生孤立 tool 消息，API 直接拒绝）；**压缩后插解释性 system 消息**（不然模型对记忆断层困惑）。

**跨会话**：wz-agent 运行时不做跨会话记忆——每次运行落在 `runs/<时间戳>/` 独立工作区（`runtime.py`），阶段间上下文只靠 spec.md 传递；`PROGRESS.md` 是开发 wz-agent 项目本身用的进度文件，不是运行时记忆。

## 第 4 章 工具：手脚

### 4.1 是什么

工具决定模型**能做什么**。每个工具对模型是一份"说明书"：

```
工具 = 名字 + 描述 + 参数 schema + （你代码里的）执行函数
```

模型读前三样（随每次请求发送，构成静态前缀的一部分），harness 执行第四样。**模型永远不能自己执行任何东西**——它只能"请求"调用。换句话说：**没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上**。这是 agent 安全性的根基。

### 4.2 工具设计的通用原则

| 原则 | 要点 |
|---|---|
| 接口清晰 | 命名直观、参数有例子、边界有说明 |
| 粒度权衡 | 太粗（bash 一个工具管所有）浪费 token 易出错；太细（每操作一个工具）增加选择负担 |
| 描述的艺术 | **工具描述是写给模型看的 UI**——描述越准，模型选择越准 |
| 参数保真 | 避免"把结构化数据压成字符串"这类有损传递 |
| 故障安全默认值 | 所有能力默认关闭，必须显式开放 |

### 4.3 业界工具生态

| 选项 | 定位 | 采纳原因 | 适用场景 |
|---|---|---|---|
| 原生 function calling | 模型 API 内置 | 零依赖、各家原生支持 | 自研 agent 首选 |
| Schema 库（Pydantic 等） | 类型系统定义工具 | 校验强、IDE 友好 | 复杂参数类型 |
| **MCP（Model Context Protocol）** | 开放标准：工具从外部服务器发现和调用 | 生态爆发——2026-07 注册表 1.8 万服务器、月 SDK 下载 4 亿次 | 接入第三方工具 |

三层关系（易混）：function calling = 模型能力；OpenAI tools API = SDK 封装；MCP = 传输协议（工具托管在独立服务器，客户端动态发现）。**它们不是竞争关系，是组合关系。** MCP 已成业界标准，但生态质量参差——机器验证显示注册表仅约 15% 的服务器可验证存活。

### 4.4 wz-agent 的实现

四件套（read/write/edit/bash）+ 反射自动生成 schema（`tools/base.py:62`）：

```python
_TYPE_MAP = {int: "integer", float: "number", bool: "boolean", str: "string"}

def to_openai_function(self) -> dict:
    sig = inspect.signature(self.run)
    # 类型注解 → properties；无默认值 → required
```

子类即普通代码（`read.py`）：

```python
def run(self, path: str, lines: str = "") -> str:
    ...   # path 必填、lines 可选（如 "1-50" 按行范围读）——自动进 schema
```

设计动机：手写 JSON schema 繁琐易错，反射让"实现"与"说明书"**永不失同步**——改签名，schema 自动跟着变。

**edit 工具的三约束**（体现"粒度与安全"原则）：oldText 必须唯一匹配（防错杀）、新旧不同（防无意义替换）、**替换后回告行号**（给模型重新对齐的信号——行号会幻觉，文本不会）。

**防御性解析**（坑#7）：模型给的 arguments 是字符串 JSON，可能不合法——try 解析、失败回喂，**工具层异常不杀死循环，变成模型的观察**：

```python
try:
    tool_args = json.loads(call["function"]["arguments"])
except json.JSONDecodeError as e:
    result = f"[ERR] 参数解析失败: {e}"   # 回喂重试
```

## 第 5 章 ReAct 循环：让三者协同

### 5.1 是什么

前三个组件是静态的，**ReAct（Reasoning + Acting）循环是把 LLM、上下文、工具串联起来的引擎**（harness 的③引擎层）——它的本质是通过不断追加轨迹来让模型持续推进任务。

循环包含三个环节：思考→行动→观察→再思考。最小骨架（伪代码）：

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory     # 组装上下文 = 静态前缀 + 轨迹
    decision = Model(context)               # 模型决策
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer              # 纯文本 → 任务完成

    for call in decision.tool_calls:        # 工具调用（可并行）
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)      # 观察追加进轨迹
```

**这是 Agent 与 Chatbot 的本质区别**：有没有这个循环。模型单次调用只能输出文本；循环让它能"持续工作"。

### 5.2 wz-agent 的实现

`src/agent/loop.py:322` `_run_loop`——上面骨架的产品化版本：

```python
while step < max_steps:                    # 硬上限，防死循环
    content, tool_calls = call_llm(messages, tool_schemas)
    if tool_calls:
        messages.append(assistant_msg)      # 记录决策（追加轨迹）
        for call in tool_calls:
            if step >= max_steps: break     # 同回复内也拦
            result = dispatch(call)
            messages.append(tool_result)    # 观察回喂
    else:
        return content                      # 纯文本 → 完成
```

轨迹演化示例（任务："修掉 utils.py 的 TODO"）：

```
[用户] 修掉 utils.py 的 TODO
[助手] read("utils.py")          → [结果] 文件内容…
[助手] edit(oldText, newText)    → [结果] 替换成功
[助手] bash("pytest")            → [结果] 2 passed
[助手] "已修复 2 处，测试通过"     ← 无工具调用，循环结束
```

真实实现多出的细节，各来自真实踩过的坑：

| 细节 | 原因 | 坑 |
|---|---|---|
| surrogate 清洗 | Windows 管道混入非法字符，API 序列化崩 | #5 |
| `[API-ERR]` 不重试 | 429/断网重发同样请求白烧钱 | — |
| 双重步数检查 | 模型一次回复连发多个调用 | — |

### 5.3 要不要用框架

业界 2026 共识：**两三个工具的线性流程不需要框架**——自研循环或轻量 SDK 足够。主流框架速览：

| 框架 | 一句话定位 | 何时选它 |
|---|---|---|
| LangChain | LLM 应用的**零件库**：模型封装、prompt 模板、600+ 集成，用管道串成线性流水线 | 要快速组装、频繁换集成（向量库/工具/模型） |
| LangGraph | Agent 的**图式编排引擎**：工作流建模为状态图（节点=步骤、边=流转），原生支持循环、分支、暂停人审、断点恢复 | 多阶段复杂工作流、需可恢复执行 |
| OpenAI Agents SDK | 官方轻量框架，handoff 交接模型 | 快速原型、OpenAI 生态 |
| CrewAI | 角色化多 agent 团队（"crew"） | 多角色协作演示 |

易混点：LangChain 和 LangGraph 不是竞争关系，是同一生态的两层——LangChain v1.0 起，其 Agent 就是构建在 LangGraph 之上的。

框架的价值在复杂状态管理和可观测性，代价是抽象层和学习成本。

wz-agent 的选择：**自研 100 行循环，零框架**——需求（单循环+四工具）远未到需要图编排的复杂度，且学习阶段可见的循环胜过黑盒抽象。

## 第 6 章 Harness：模型之外的竞争力

### 6.1 Harness 到底是什么

第 1 章的边界图已经给出答案，这里正式展开：**Harness = Agent 边界内、模型之外的一切**。它是大脑的载具——马具不是限制马奔跑，而是把力量引导到正确方向。

四个常被误问的归属问题：

| 问题 | 答案 | 原因 |
|---|---|---|
| 工具调用属于 harness 吗 | ✅ | "决定调哪个"是模型，但执行、校验、分发、回喂都是你的代码 |
| ReAct 属于 harness 吗 | ✅ | 循环是你写的 while；模型只负责循环体内"单次决策"那一行 |
| 记忆系统属于 harness 吗 | ✅ | 模型每次调用都无状态；是 harness 把历史拼回上下文让它"记得" |
| 系统提示词属于 harness 吗 | ✅ | 它是 harness 组装进上下文的静态前缀（设计物） |

检验标准只有一条：**换个模型，它还成立吗？** 成立的都是 harness。

生产实践给出的核心判断：

> **模型能力正在商品化，真正的差异在于 Harness。** 生产级 Agent 系统的绝大部分代码都在做保障机制，而不仅仅是上下文和工具本身。

Harness 五要素 = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正，构成一个闭环：上下文与工具支撑决策，约束预防错误，验证发现偏差，纠正闭合循环。缺少任何环节，系统都有可靠性缺口。注意：前两个要素就是第 3、4 章讲的"眼睛与手脚"——**它们本来就是 harness 的核心，保障层是生产化时补上的另外三件**。

### 6.2 五要素：harness 的功能地图

| 要素 | 核心原则 | wz-agent 的实现 |
|---|---|---|
| **上下文管理** | 信息充分性：每个决策点都基于足够信息 | spec.md 蒸馏 + `_maybe_compact`（第 3 章） |
| **工具接口** | 接口清晰：命名直观、参数有例、边界有说明 | 反射 schema + edit 三约束（第 4 章） |
| **约束** | 故障安全默认值：能力默认关闭，显式开放 | bash 三层防线（下详） |
| **验证** | 输入隔离：安全检查只看结构化数据 | tickets 分诊 + 测试驱动 |
| **纠正** | 确认无法恢复前不暴露中间态 | 失败回喂 + 3 次上限熔断（下详） |

### 6.3 约束的实例：bash 三层防线（`tools/bash.py`）

```python
_DANGEROUS_PREFIXES = ("rm -rf /", "rm -rf ~", ...)  # 第1层：无条件拦截
# 第2层：plan 模式下命令先攒进清单，延迟到收集完才批量执行
# 第3层：30s 超时 + Windows 进程树清理（taskkill /T）
```

一个易漏的细节：**plan 模式下工具的 description 也随之改变**（追加"当前处于计划模式"）——权限状态必须同步进模型认知，否则它以为自己执行了。两个 Windows 深坑（#3 stderr 解码崩、#4 子进程杀不干净）提醒：**没有超时和进程清理的 bash 工具不是安全问题，是可用性问题**。

### 6.4 纠正的实例：失败回喂 + 熔断（`loop.py::run_with_retry`）

```
工具报错 → 错误信息作为工具结果回喂 messages → 模型自己修
         → 同一处连续失败 3 次 → 停下来问人（熔断）
```

两条失败通道分流——**不是所有失败都值得自愈**：

| 失败类型 | 例子 | 处置 |
|---|---|---|
| 任务失败 | 语法错误、测试挂 | 回喂重试（模型能自修） |
| 环境失败 | 429 限流、断网 | 直接终止（重发白烧钱） |

### 6.5 验证的实例：任务系统（`issues.py` + triage/tickets）

长任务单循环会迷路（目标稀释在工具结果海洋里）。wz-agent v2.0 加了人机分工协议：

```
triage:      .scratch/ 的 markdown issue → LLM 按五标签状态机分诊
             标签: needs-triage → ready-for-agent / ready-for-human / needs-info / wontfix

to-tickets:  spec.md → 拆解为垂直切片 tickets（每个 = 端到端可验证的最小功能）
```

**垂直切片**优于水平分层：先写完所有数据层再写所有界面（水平），agent 写界面时要记住很久前的数据层约定——上下文压力大；每个 ticket 端到端可验证（垂直），自包含、做完即验证。工程决策：**编号唯一性由代码保证，不信 LLM**——"精确性"责任永远归 harness。

### 6.6 人机交互：知情 ≠ 批准

wz-agent 的三通道监督（粒度递增）：

```
通知 <─ checkpoint（非阻塞："已生成 3 个文件，继续"）
提问 <─ ask_user（模型主动："数据库用 SQLite 还是 Postgres？"）
打断 <─ Ctrl-C（用户随时：菜单选 继续/注入指令/终止）
```

配套 `runtime.py` 的可回放工作区：每次运行 `runs/<时间戳>/` 存 spec、代码、session.log——**Agent 的行为要可审计**，跑完就丢的 agent 无法调试、无法复盘、无法信任。
